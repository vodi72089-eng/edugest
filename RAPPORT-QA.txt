                          FINDINGS (par gravité)

--------------------------------------------------------------------------------
[P1 — CONFIRMÉ LIVE] IDOR lecture config devise : GET /api/school-currency
--------------------------------------------------------------------------------
Fichier    : src/app/api/school-currency/route.ts (GET, L8-L35)
Faille     : requirePermission('school:read') mais le schoolId du QUERY est
             utilisé tel quel, SANS verifySchoolAccess(user, schoolId).
Preuve     : SECRETARY claudine@lumiere.cd (école s1) :
               GET /api/school-currency?schoolId=<Kivu s2>
               → 200 avec la VRAIE config de s2 :
               {"id":"cmufzmltt0000tkxkpgdh3z0t","schoolId":"cmud3g97k0005tk74ncj1dgjj",
                "baseCurrency":"USD","displayCurrency":"USD","enabledCurrencies":"USD,CDF",...}
             SCHOOL_ADMIN admin@brazza.cd (s2) → lit la config de s1 en 200.
Impact     : n'importe quel rôle avec school:read (SECRETARY, DIRECTION,
             SCHOOL_ADMIN...) peut lire la configuration financière de
             TOUTE école concurrente en devinant/générant un schoolId.
             (Quand aucune config n'existe, des valeurs par défaut sont
             renvoyées — fuite de moindre gravité.)
Remarque   : l'IDOR est reproductible quel que soit le schoolId passé.

--------------------------------------------------------------------------------
[P1 — CONFIRMÉ, PUIS CORRIGÉ PENDANT LA PÉRIODE DE TEST] IDOR whatsapp-config
--------------------------------------------------------------------------------
Fichier    : src/app/api/whatsapp-config/route.ts
État initial (22-24/09) : GET lisait searchParams.get('schoolId') sans aucune
             vérification (requireAuth seul) → TOUS les comptes (SECRETARY,
             PARENT, CASHIER, DIRECTION...) recevaient 200 avec
             schoolId=<n'importe quelle école>. Data null à l'époque (pas de
             config seedée) mais le canal était ouvert.
État actuel (26/09) : CORRIGÉ — whitelist WHATSAPP_CONFIG_ROLES
             [SAG, SCHOOL_ADMIN, SECRETARY] + schoolId honoré UNIQUEMENT pour
             SAG, sinon user.schoolId forcé.
Re-test     : PARENT/CASH/DIR/HEAD → 403 ; SECRETARY ne reçoit que sa propre
             école ; SAG → 200 sur s2 (légitime). ÉTAT : OK après fix.
Note       : si le fix n'est pas encore commité, il doit l'être.

--------------------------------------------------------------------------------
[P2 — CONFIRMÉ LIVE] GET /api/schools public sans authentification
--------------------------------------------------------------------------------
Fichier    : src/app/api/schools/route.ts
Faille     : GET accessible sans token (requireAuth optionnel).
Preuve     : GET /api/schools sans Authorization → 200, 6 écoles, champs :
             id, name, shortName, city, province, schoolCategory, schoolType,
             isActive, createdAt, logo, coverImage et _count.
Impact     : fuite des métriques internes (_count students/classes/users par
             école) + inventaire complet des écoles avant authentification.
             Partiallement "by design" (annuaire public), mais _count et les
             IDs internes n'ont rien à faire dans une réponse publique.
Recommandé : page publique = champs marketing seulement ; compteurs agrégés.

--------------------------------------------------------------------------------
[P2 — CONFIRMÉ LIVE] POST /api/schools sans authentification
--------------------------------------------------------------------------------
Faille     : création de compte école entièrement anonyme.
Preuve     : POST /api/schools (aucun header Auth) avec name/shortName/email/
             phone/city/province/country → 201, école créée (FREEMIUM) +
             admin généré avec mdp aléatoire envoyé (flux d'inscription).
             (Données créées nettoyées après test.)
Impact     : spam d'inscription d'écoles ; vérifié : rate-limit par IP présent
             (évalué : limite l'abus mais pas d'email/captcha de vérification).
Gravité    : modérée — fonctionnalité d'inscription vouue publique, à durcir
             (captcha, vérification email, modération admin avant activation).

--------------------------------------------------------------------------------
[P2 — CONFIRMÉ LIVE] POST /api/school-comments sans rate-limit
--------------------------------------------------------------------------------
Fichier    : src/app/api/school-comments/route.ts
Preuve     : 3× POST sans auth → 201 en moins de 100 ms (aucun throttling).
             (Commentaires créés avec isApproved=false ; nettoyés après test.)
Impact     : spam illimité en base (bombardement d'avis). La modération
             (isApproved) limite la diffusion publique mais pas le remplissage
             de la DB ni le coût de modération.
Remarque   : le rate-limit IP de POST /api/schools montre que le pattern
             existe déjà dans la codebase — il est simplement absent ici.

--------------------------------------------------------------------------------
[P3] Routes "read by ID" sans vérification d'école
--------------------------------------------------------------------------------
Fichiers   : api/convocations/[id]/read, api/grades/[id]/read,
             api/homework/[id]/read, api/communications/[id]/approve
Faille     : accès par ID séquentiel (cuid) sans verifySchoolAccess sur
             l'objet chargé. Nécessite une session valide, et les IDs CUID
             sont difficiles à deviner → gravité faible, mais un utilisateur
             d'une école qui obtient un ID (ex. fuite d'email/URL) peut lire
             des données d'une autre école.
Existant   : 71 des 128 routes API n'appellent pas verifySchoolAccess —
             surface à auditer unitairement (beaucoup se scopent via
             user.schoolId dans le WHERE, ce qui est correct).
